The editor is where you read, write, and collaborate on your docs, and where AI agents land when they edit. WYSIWYG by default with a source-mode toggle, a frontmatter properties pane, real-time CRDT collaboration, and a file sidebar that organizes the project.

## Open a single file

Want the editor on one loose markdown file without setting up a project? Run `ok <file>`:

```bash
ok notes.md            # open a single file in the editor
ok ./specs/foo/SPEC.md # a file inside a project opens that project, focused on the doc
```

When the file is inside an existing GitQuire project, this opens that project focused on the doc. When it's a loose file, it opens an **ephemeral single-file session**: a throwaway editor scoped to just that one file, with no project scaffolding or git. Your edits save straight back to the original file, and **nothing is written into the file's directory** — all session state lives in a temporary directory that's removed when you close the window. Opening a file you don't edit leaves it byte-for-byte unchanged.

Single-file sessions own only the selected file. Different-file previews can coexist, but an enclosing project cannot start until its overlapping preview closes. File uploads and project-wide configuration changes require opening a project; they cannot create files beside a loose preview. Appearance settings and document comments remain available. See [overlapping projects and previews](/docs/reference/cli#overlapping-projects-and-previews) for nested-project boundaries and restart requirements.

It opens in the desktop app when it's installed, and falls back to your browser otherwise (press Ctrl-C in the terminal to end a browser session). Single-file sessions use the shared header and editor card without a project file sidebar, project tabs, or project switcher. At narrow widths, the header lets you choose Editor, Agents, or Terminal where available and return to Editor. Discover it any time with `ok --help`.

On Windows, you can also open `.md` and `.mdx` files from Explorer with **Open With → GitQuire**, or double-click them when GitQuire is their default app. With the desktop app installed, these actions open a project or a standalone file using the same rules as `ok <file>`; see [Windows file associations and changing the default app](/docs/reference/what-gitquire-writes#installing-and-launching-the-app).

## Document body

Open any doc from the sidebar. The body renders as WYSIWYG markdown with familiar conventions: bold / italic / headings / lists / tables / code fences / links / images. Toggle to source mode from the editor controls or with `Cmd+Option+M` to edit the raw markdown directly; both views are bound to the same CRDT document, so they stay in sync across users and AI agents. Switching modes keeps your place — the block you were looking at stays in view either way.

A slash command (`/`) opens an insert menu for headings, lists, tables, code blocks, callouts, footnotes, inline math, and the other content shapes the editor supports.

When a doc ends in a table, list, or code block, click the empty space below it to start a new paragraph there. A **+** appears in the gutter as you hover, showing where the line will land. On a touch device there is no hover to read, so the **+** stays visible whenever that space is there to use, and on a narrow screen it sits at the left edge of the text rather than out in the gutter. The space is only a click target, so nothing is written to the file until you use it, and a doc that ends in a table stays ending in a table.

A doc written before this behavior may still carry a blank line at the end that nobody typed. GitQuire leaves trailing blank lines alone rather than removing ones it did not write, so clear it with **Auto-fix** in the Problems panel, with `ok lint --fix`, or by hand. See [markdownlint rules](/docs/advanced/content-rules/markdownlint).

Markdown problems (hard tabs, heading increments, and the rest) are flagged inline as you write, with a **Problems** panel in the document panel for the whole doc or project. See [Content rules](/docs/advanced/content-rules/overview).

### Undo in source mode

This section is about the Markdown source pane only. The visual editor keeps its own undo history, and none of what follows changes it.

Undo in source mode covers the editing you did there. Switching to the visual editor for a look and coming straight back leaves that history intact. But if you leave source mode, by switching to the visual editor or by moving to another tab, and anything writes to the document while you are away, source-mode undo and redo start fresh when you come back. Many things count as a write, not only the obvious ones: your own edits in the visual editor, an agent, a collaborator, a change on disk, a field you change in the **Properties** panel, a fix applied from the **Problems** panel or from the visual editor, or the tail of a large paste you started in source mode that was still landing as you flipped away. Restoring an earlier version from the [Timeline](./timeline-and-recovery.mdx) counts as a write too, so if you restore while you are out of source mode, undo there starts fresh when you come back. Source-mode undo history belongs to the current document session: navigating through enough other documents to evict it, or closing and reopening the app, starts it fresh even if no one rewrote the file.

No text is removed when that happens. One case is still not covered. If a rewrite lands while you are sitting in Markdown source rather than away from it, the history is left as it is, so a single undo can still take back more than you expect.

To go further back, the [Timeline](./timeline-and-recovery.mdx) keeps earlier versions of the whole document. Each entry is a snapshot of the whole document. Agent edits, human edits, and file-system changes are batched into an entry once activity settles. Upstream syncs get their own entry when the sync lands. Restoring an entry brings back that version's content. Restoring is append-only, so the edits you made since then stay on the timeline and you can restore back to them.

### Lists

Hover over a bullet, numbered, or task-list item and drag its grip to move that item within the list or elsewhere in the document. Nested items have their own grips; select several items or a passage spanning multiple blocks before dragging to move them together. Task checkboxes keep their checked state. Reordering a numbered list's items, or moving items into or out of one, renumbers that list's items sequentially from its starting number, replacing custom gaps or repeated numbers. Moving a whole numbered list preserves its authored numbers unless its items merge into another list.

To reorder with the keyboard, place the cursor in an item or select several neighboring items, then press `Cmd+Shift+↑` or `Cmd+Shift+↓` on macOS (`Ctrl+Shift+↑` or `Ctrl+Shift+↓` on Windows and Linux). At a list's edge, the same shortcut moves the selection past the neighboring block or out of its parent item.

### Tables

Insert a table from the slash menu. The header row stays visible as you scroll down a long table, the first column stays pinned as you scroll sideways, and dragging a row or column handle reorders it. Cells are single-line in the stored markdown: pressing Enter inside a cell — or pasting a table whose cells hold lists or paragraphs — joins the lines with `<br />`, the GFM line-break idiom, so the table stays valid for everyone else opening the file. `<br>` tags in existing files render as real line breaks and round-trip byte-for-byte.

Aliased wiki links and embeds must escape their separator inside a table cell: write it as `\|`, since a bare `|` ends the cell. `[[Page\|alias]]` in a cell resolves identically to `[[Page|alias]]` outside one, and the escape you author is preserved in the saved file. Two corners escape that preservation, and only the first is about cells. In a cell of any table rather than only a migrated one, a code span or raw HTML whose own content holds a backslash immediately before a pipe gains a second backslash on save. That extra backslash stops the pipe from reading as an escape, so the cell ends at that pipe and the value is cut in two. GitQuire then shows the tail as an extra cell in that row, or stops parsing the block as a table when the affected cell is in the header row; other readers differ on the same bytes, and some drop the tail instead of showing it — so treat anything after that pipe as at risk rather than merely misplaced. The second corner is not a table phenomenon and does not strike on save: an aliased wiki link or embed whose alias holds that same pair, anywhere in a document, is written to the file with the backslash intact and comes back without it the next time the file is opened. Nothing is cut in two and no row breaks, so the only cue is the alias itself reading `a|b` where you wrote `a\|b`. Neither corner is reachable by writing the source: both arrive by pasting, or by editing the cell or the alias in place. Writing `\|` as an alias separator, or inside a code span in a cell, stays the correct form and is preserved as authored.

### Mermaid diagrams

A `mermaid` code fence renders as a live diagram (the slash menu can insert one). On-diagram buttons pan, zoom, and reset the view; mouse-wheel zooming and drag panning are disabled so a large diagram never moves while you scroll past it.

### Live HTML embeds

An `html preview` code fence renders its contents live in a sandboxed iframe instead of showing the source. The slash menu's `/embed` group inserts starters — a blank theme-aware page, a chart, stat cards, custom SVG, an interactive control — that open straight into the preview.

### Underline

`Cmd+U`, or the Underline button in the selection bubble menu, underlines the selection. Markdown has no underline syntax of its own, so it saves as inline HTML: `<u>underlined</u>`. `<ins>…</ins>` — what Joplin and Logseq write — is read as underline too, whether it arrives on the clipboard or is already sitting in a file you open, and each file keeps the spelling it arrived with instead of being rewritten under you. Both underline in GitQuire and in any renderer that passes inline HTML through. GitHub is the exception worth knowing: it renders `<ins>` underlined but strips `<u>` back to plain text, so the words survive and the underline doesn't.

### Markdown Comments

Notes that stay in the file and out of what a reader sees. (For comment threads attached to a passage, see [Comments](/docs/gitquire/comments).) GitQuire reads two syntaxes. There's no button or shortcut for either — you type them, inline inside a paragraph or as a standalone block spanning several lines:

| Syntax | Hidden from readers in |
| --- | --- |
| `<!-- note -->` | Everywhere. It's an HTML comment, so no markdown renderer ever shows it to a reader. |
| `%%note%%` | GitQuire and Obsidian, which share the convention. Everywhere else it renders as ordinary text, percent signs and all. |

So: reach for `<!-- -->` when the file will be read outside GitQuire — pushed to GitHub, built into a docs site, opened in another editor. Reach for `%%…%%` when the file round-trips through Obsidian, whose own comment syntax this is. The syntax you type is the syntax that gets saved: GitQuire never converts `<!-- -->` into `%%…%%` or back. Two tidyings happen on save, and only these two. A multi-line `%%` block takes the padded shape, with a blank line after the opening delimiter and before the closing one. And an HTML comment gets one space of inner padding, so `<!--note-->` saves as `<!-- note -->`. The `%%` inline form keeps its body exactly as typed, spaces included.

In the editor, comments stay visible and editable: dimmed and italic under a dashed underline, with a dashed left rail on the block form. The underline is what tells a comment apart from ordinary emphasis without relying on colour. The delimiters themselves aren't drawn, the same way the editor doesn't draw the asterisks around bold — switch to source mode to see or edit them. That means the two forms look identical in the editor: which one a given comment uses is a real decision, per the table above, and source mode is where you check it. The body stays on screen either way, which is deliberate: text you typed should never disappear from the surface you typed it into.

Two limits are worth knowing. The first applies mid-sentence only: a comment inside a line of prose whose body is *nothing but* a formatted word — `%%**bold**%%` — stays ordinary prose rather than becoming a comment, because there is no way to record whether the emphasis sat inside the comment or the comment inside the emphasis. Give it any plain text alongside (`%%note **bold**%%`) and it is recognized normally. The same comment alone on its own line is recognized either way, as a comment block.

The second is a budget: a paragraph, heading, or table cell can carry **one** comment whose body contains formatting. Write two in the same one and neither is recognized — both stay literal `%%`, and worse, the word between them can be claimed as a comment instead and disappear from published output. Split them across separate paragraphs, or keep one of the two bodies plain.

Readers don't see them. Wherever GitQuire renders a doc to HTML rather than to the editor, both forms come out as real HTML comments, which browsers don't display. Copying a passage out of GitQuire leaves the comments behind too, so an annotation can't ride along into an email or a chat message. In-app read-only views — the rendered diff, the skill viewer — do keep showing them dimmed: there the whole point is to show you everything the document contains.

### Find and replace

`Cmd+F` opens find in the visual editor; `Cmd+Option+F` (`Ctrl+H` on Windows / Linux) adds the replace controls. `Cmd+G` and `Shift+Cmd+G` step through matches.

## Links

Links work the way they do in the editors you already know:

- **Type a URL, then press space or enter.** A full URL (`https://…`, `www.…`, or an email address) becomes a link when you press space or enter after it. Plain words and filenames like `AGENTS.md` are left alone, and one `Cmd+Z` turns a conversion back into plain text.
- **Paste or drag in a URL.** Pasted (or dropped) on its own, it becomes a link. Pasted over selected text, it links that text instead — the text stays, the URL becomes its destination. `Cmd+Shift+V` pastes plain, with no linking.
- **Type `[text](url)`.** Closing the parenthesis converts the markdown shorthand into a real link; `Cmd+Z` restores the literal text.
- **Link to a section.** Append `#` and the heading's slug to a doc link — `[text](./spec.md#data-model-v2)` — and the WYSIWYG editor opens the doc scrolled to that heading (the source editor ignores the fragment and opens at the top). The slug is the heading text in lowercase with accents on Latin, Greek, Cyrillic, Arabic and Hebrew letters dropped (other scripts keep their marks, so `## ガラス` stays `ガラス`), every run of characters that aren't letters or digits replaced by one hyphen, and hyphens trimmed from both ends: `## Data model: v2` becomes `data-model-v2`, `## FAQ:` becomes `faq`, and a second identical heading in the same doc gets `-1`. Agents write the same form in chat, so a reply about one part of a long spec can take you straight to it.
- **Press `Cmd+K` with text selected.** The link popover opens with the URL field focused, pre-filled from your clipboard when it holds a URL. With the cursor inside an existing link, `Cmd+K` opens that link for editing. With no selection, `Cmd+K` keeps opening the command palette, as everywhere else. To reach the command palette while text is selected, use `Cmd+P` (`Ctrl+P` on Windows / Linux), which always opens it.

For legacy wiki links and ambiguous names, see [how links resolve and what to review after upgrading](../reference/core-concepts.md#review-links-after-upgrading).

## Right-click menu and spell check

In the desktop app, right-clicking editable text opens a native context menu. Any editable field gets **Cut / Copy / Paste / Select All**; when there's a selection or a flagged word under the cursor, **Search with Google** joins it — plus, on macOS, **Look Up** (the dictionary panel).

Over the document body, the menu also carries **View in Source `</>`** — the desktop equivalent of `Cmd+Option+E`, opening the Markdown behind the block you right-clicked in the visual editor.

Spell checking uses the native macOS spellchecker on macOS (language follows your macOS settings) and Chromium's built-in spellchecker on Windows and Linux, so misspelled words get the familiar red underline. Right-clicking a flagged word adds the spelling section:

| Item | Behavior |
| --- | --- |
| *Suggestions* | The spellchecker's corrections, one row each; pick one to replace the word. |
| **Add to Dictionary** | Teaches your system dictionary the word — persistent and, on macOS, shared with your other Mac apps (Safari, Notes). |
| **Disable Spell Check** | Turns spell checking off app-wide. The choice persists across relaunches. |

While spell check is off, right-clicking any editable text offers **Enable Spell Check**, and the menu bar carries the same toggle as **Edit ▸ Check Spelling While Typing** (see [Edit menu](#edit-menu)). You can also change **Check spelling while typing** in **Settings → User → Preferences**, beside **Language**. These controls share the same app-wide preference.

On Windows and Linux, **Spelling languages** lets you check multiple languages together, such as English and Vietnamese, independently of the interface language. The choice applies across projects in the same desktop profile and survives a restart. Keep at least one language selected; use the spelling toggle to turn checking off without losing your languages. On macOS, checking languages remain managed by macOS.

Uncached dictionaries may download from Google's dictionary CDN; document text and typed words are not sent to Google for spell checking ([Electron's spellchecker documentation](https://www.electronjs.org/docs/latest/tutorial/spellchecker#does-the-spellchecker-use-any-google-services)). Downloads need an internet connection, and existing underlines may not update immediately after changing languages.

Surfaces with their own specialized right-click menus — asset and wiki-link chips, the [file sidebar](#right-click-context-menus), editor tabs — keep them; the editor menu never doubles up on top. In the web build the browser's own context menu fills this role.

## Comment on a selection

Select text in the WYSIWYG editor and the selection bubble menu shows a **Comment** button alongside the formatting controls. Clicking it — or pressing `Cmd+Shift+M` — starts a [comment thread](/docs/gitquire/comments) on the selection, stored in the page.

## Header panes

The **Agents** button at the right end of the header shows and hides the Agents panel in project windows and single-file windows on desktop and on the web, and is highlighted while the panel is open. `Cmd+L` on macOS or `Ctrl+L` on Windows and Linux shows and hides it too. The panel holds the [AI chat](/docs/gitquire/ai-chat).

The **Editor** button comes first in the same group, before **Agents** and **Terminal**. It appears in project and single-file windows on desktop and on the web, but not in note windows, and is highlighted while the editor is shown. In a window narrower than 48rem it selects Editor, including when returning from Agents or Terminal; see [Narrow windows](#narrow-windows). Project windows can also hide Editor; see [Hide the editor](#hide-the-editor).

The editor, the Agents panel and the terminal split the window by proportion. Drag the gap between two of them, or focus it and use the arrow keys, to change their shares; each project remembers its own arrangement. Opening a panel never closes another one to make room. Dragging a gap stops at each panel's minimum size; when there is not room for the open panels' minimum sizes, they shrink below them in proportion, so a right-side Terminal between the editor and the Agents panel can drop under 40 columns. Below 48rem only one of Editor, Agents and Terminal is shown at a time; see [Narrow windows](#narrow-windows).

To move a panel, drag an empty part of its tab strip (the editor's row of tabs, or the Agents or Terminal tab strip) onto another panel; with only one panel open there is nowhere to move it, and the drag does nothing. Drop it within about a quarter of the way in from one of that panel's edges and it docks on that side, in the area the outline shows; drop it nearer the middle and the two panels swap places. Pressing a tab or a button in the strip starts no move, and `Esc` cancels one. In the desktop app's project and single-file windows these strips never move the window, even with one panel open, so drag the header at the top of the window to move it; note windows have no panels to move, and their header still moves the window. The command palette can also move a panel along a whole edge of the window and show it: search for **Move Editor to the left edge of the window**, **Move Agents to the left edge of the window** or **Move Terminal to the left edge of the window**, or the same for the right, top or bottom edge. These commands are not in the menus and appear only when you search, and the Terminal ones only in the desktop app, where a terminal can run. They also reach a panel whose tab strip has no empty space left to grab. **Move Terminal to right** and **Move Terminal to bottom** are different: they put the Terminal beside or below the editor.

## Hide the editor

In a project window you can hide the editor and give the window to the Agents panel and the terminal. At 48rem and wider, click the **Editor** button at the right end of the header; at any width, choose **View ▸ Show / Hide Editor** in the desktop app or search `editor` in the [command palette](#command-palette). Below 48rem the **Editor** button only selects Editor, and hiding it works as described in [Narrow windows](#narrow-windows). There is no keyboard shortcut for it. Single-file windows keep Editor available in the shared header but can show another supported component instead while narrow. Note windows remain editor-only.

Hiding the editor hides all of it: the file sidebar, the tabs, the document, the document panel, the status bar with the checkout line (the project folder and the branch or worktree). Nothing reloads. Open documents, tabs, the file sidebar and the document panel stay loaded, and showing the editor brings them back as they were.

The panels that are still open take over the editor's space, shared in proportion to their sizes among the panels in the same row or column as the editor. With the Agents panel at the right and the Terminal below or to the right of the editor, where **Move Terminal to bottom** and **Move Terminal to right** put it:

- A terminal below the editor fills the column they share, top to bottom, and beside the Agents panel that column takes the same share of the row whether the editor is shown or hidden.
- A terminal to the right of the editor and the Agents panel divide the row in the ratio of their shares, as far as each one's minimum width allows.
- A single remaining panel fills the window.
- The Agents panel on its own keeps the conversation and the message box at a comfortable reading width, centered.

Sizes you drag while the editor is hidden are kept. In the arrangements above, a terminal below the editor shares its column with it, so dragging the gap beside the Agents panel also sets the editor's width; with the terminal to the right of the editor, the editor keeps its own size.

Any deliberate way of opening a document shows the editor again with that document: search and quick open, links in the Agents panel and the terminal, an agent navigating, deep and share links, back and forward, creating a page, the sync badge, dialogs that open a file, and opening the document that is already active. Editor shortcuts and menu actions show the editor first and then act: the tab shortcuts, reopening or closing a tab, **New File**, **New Folder**, **New from Template…**, **Rename**, **Duplicate**, **Move to Trash**, showing or hiding the document panel or the file sidebar, the file sidebar's view options (hidden files, `.ok` folders, Markdown only, the skills section) and **Expand all** / **Collapse all**, **Skills**, **Blob Run**, **Initialize starter pack** once it applies, and **View in source**. Reloading the window or restarting the app never shows a hidden editor.

While the editor is hidden, `Cmd+L` (`Ctrl+L` on Windows and Linux) still shows and hides the Agents panel.

Whether the editor is shown is remembered: in the desktop app per project, including across a full app restart, and on the web in your browser. A **Hide Editor** in a window narrower than 48rem lasts only for that window's session and does not change this setting.

### Nothing open

When the editor, the Agents panel and the terminal are all hidden, the main area shows **Nothing open** with **Open editor**, **Open agents** and **Open terminal** buttons. **Open terminal** appears only where the **Terminal** button would, so not on the web or in a project with the terminal turned off. Quitting with every panel hidden reopens to **Nothing open**.

## Narrow windows

When a project or single-file window is narrower than 48rem (768px at the default text size), it shows one of Editor, Agents and Terminal at a time instead of side by side. The **Editor**, **Agents** and **Terminal** buttons in the header join into one switcher that selects which one you see, with the shown one raised; pressing the one already shown does nothing. The others keep running while hidden: chats keep streaming, shells keep their output, and drafts, tabs, scroll positions and undo history are kept for when you switch back.

- The component you used last is selected when the window narrows. Opening a document from search, history, a link, the terminal or a chat selects Editor with that document.
- **Hide Agents** or **Hide Terminal** (from the View menu, the command palette or `Cmd+L` for Agents) returns to Editor. **Hide Editor** shows an Agents or Terminal session that is already open, or **Nothing open** if none is.
- Refreshing keeps the selection in the same window or tab. A new tab or window starts with Editor.
- Widening the window restores the layout you had at full width. Choosing a component or hiding one while narrow does not change which panels open when the window is wide again, but closing a chat or terminal session closes it everywhere.

When the editor is too narrow to show every [split pane](#tabs-and-split-panes) side by side, it shows one pane at a time, and an **Editor pane** selector in the editor header switches between them. Each pane keeps its own tabs and reading position.

## Properties

Every doc can carry a bit of structured information at the top: a `status`, an `owner`, a `tags` list, a date. GitQuire calls these its **properties**.

In the raw markdown file, these properties live in a fenced block at the very top of the file, between two `---` lines. Markdown tools call that block *frontmatter*: it's just a small chunk of YAML, the doc's "labels." You never have to write it by hand: the **Properties** panel on the right of the editor shows each field as an ordinary form input (text, number, checkbox, date, or list) and saves your changes back into the file. Edit the panel or the raw block in source mode; changes propagate live either way.

A folder can describe itself (its own properties, just like a doc's) and offer templates that give new docs their starting properties. See [Folders and templates](../advanced/folders-and-templates.mdx#folder-properties) for how that works.

## File sidebar

The sidebar lists every file in your project on disk, including files excluded by `.gitignore` / `.okignore`, except dot-prefixed entries and tooling internals (`.git/`, `.ok/`, `node_modules/`). Turn on **Show Hidden Files** to reveal the dot-prefixed entries. Folder rows expand and collapse; file rows open in a tab on click. A file with validation problems shows a tinted row and a count badge, and clicking the badge (or tabbing to it and pressing Enter) opens that file with the Problems panel on it, see [Where problems show up](../advanced/content-rules/overview.mdx#where-problems-show-up). The project row at the top of the file list has buttons to create files and folders; search is in the header at the top of the window. At the bottom of the sidebar, the collapsible **Skills Studio** dock lists your skills next to your files, so a file and a skill can be open side by side; see [Skills Studio](./skills/index.mdx#where-to-find-skills-studio).

### Right-click context menus

Right-click anywhere in the sidebar to get a context-aware menu. Three shapes share consistent ordering so the muscle memory carries across surfaces:

| Item | Empty space | Folder row | File row |
| --- | --- | --- | --- |
| New File | yes | yes | no |
| New from template | yes | yes | no |
| New Folder | yes | yes | no |
| Reveal in Finder | yes (project root) | yes | yes |
| Share | yes (project root) | yes | yes |
| Copy full path / Copy Path ▸ | yes (full path of project root) | yes (Full / Relative) | yes (Full / Relative) |
| Show Hidden Files | yes | yes | no |
| Expand all / Collapse all | yes (tree-scoped) | yes (subtree-scoped) | no |
| Duplicate | no | yes | yes |
| Rename | no | yes | yes |
| Hide folder / Hide this file | no | yes | yes |
| Delete | no | yes | yes |

Items that depend on the desktop app (revealing in your file manager, Delete via the OS trash) are hidden in the web build. Asset rows (images, PDFs, other non-markdown files) suppress Share, Duplicate, and Hide; they keep Reveal, Copy Path, Rename, and Delete.

Expand all and Collapse all only appear when they have work to do: Expand all is hidden when no folder is collapsed; Collapse all is hidden when no folder is expanded. New from template appears when templates are available for the target folder, and also whenever its folder config has not loaded — if the load failed, the item opens to a disabled "Couldn't load templates" row. A symlink, a plain file, or an unreadable directory under `.ok/` can drop a folder's templates (hiding the item); a symlink at the folder's own `.ok` fails its config load (the disabled row) — see [where templates are stored](../advanced/folders-and-templates.mdx#where-its-stored). Share appears only when the project has a GitHub remote.

### Creating files and folders

Pick **New File**, **New from template**, or **New Folder** from any of the three menus. The sidebar shows an inline rename field at the target location; type a name and press Enter. **New from template** opens the [template picker](../advanced/folders-and-templates.mdx#templates) (the same dialog the project row's create buttons use) and respects the folder's `templates_available` cascade.

Right-click on empty space drops the new item at the project root. Right-click on a folder drops it inside that folder.

### Hiding files and folders

**Hide this file** on a file row, or **Hide folder** on a folder row, appends a matching pattern to `.okignore`. See [Ignore patterns](./ignore-patterns.mdx) for the full pattern syntax. The item disappears from the tree, search, and the agent's MCP tools immediately; nothing is deleted on disk.

### Show Hidden Files

The sidebar always lists every file on disk under the content directory (including files excluded by `.gitignore` / `.okignore`), except synthetic system docs. A single **Show Hidden Files** toggle on the empty-space and folder menus controls whether dot-prefixed entries are shown. It persists per-project per-machine in `.ok/local/config.yml` under `appearance.sidebar`, and also lives in the **View** menu.

| Toggle | Effect |
| --- | --- |
| **Show Hidden Files** | Off by default. When on, stops the client from hiding paths that start with `.` (recovers allowed dotfiles like `brain/.archived/note.md`). Tooling internals (`.git/`, `.ok/`, `node_modules/`) stay hidden in every mode. |

On very large trees the disk walk is capped per level, and the sidebar shows a notice telling you the list is partial.

### Deleting via Trash

**Delete** moves the item to the system Trash via the same `shell.trashItem` call VS Code and Finder use: recoverable, not destructive.

## Tabs and split panes

Tabs share the main editor header and shrink as the row fills, keeping every open target visible without a horizontal scrollbar. Drag a tab to reorder it. Opening a file from the sidebar uses a lightweight preview tab by default: the next single-clicked file replaces it, while double-clicking the tab title, pinning, or choosing **Keep open** from its context menu keeps it open. Turn previews off with **Settings → Preferences → Preview tabs** ([`editor.previewTabs`](/docs/reference/configuration)).

To work side by side, drag any document, folder, or **New tab** to the left or right edge of the editor. The blue drop indicator shows where the new vertical pane will open. You can also right-click a tab and choose **Move to new pane left** or **Move to new pane right**; from the keyboard, focus the tab, press `Shift+F10` (or the Menu key), then choose the same command. Drag the divider to resize panes. Each pane keeps its own active tab, while the document panel follows the pane you most recently focused. Moving or closing a pane's last tab removes the pane automatically.

Open tabs, pane order, sizes, and the focused pane are restored with the project after a clean restart. In an editor too narrow for its panes, see [Narrow windows](#narrow-windows).

## Command palette

`Cmd+K` opens the command palette in both the desktop app and the browser, and `Cmd+P` (`Ctrl+P` on Windows / Linux) does the same from anywhere — including while text is selected in the visual editor, where `Cmd+K` adds a link instead. Type to jump to any file or folder, run create commands, open the graph or settings, or dispatch to an agent; recently opened entries surface first. In the desktop app it also switches projects and worktrees. In project windows, searching `editor` finds **Show Editor** or **Hide Editor**, whichever applies, the same toggle as the header's **Editor** button (see [Hide the editor](#hide-the-editor)).

In the browser, `Cmd+P` is normally the print shortcut; GitQuire takes it for the palette, so print from the browser's own menu instead.

Remove a recent project from the list by hovering its row and clicking the ×, or right-clicking for a **Remove from recent projects** menu — the same controls are on the **Switch project** dropdown in the header at the top of the window and in the Project Navigator. A recent whose folder was deleted or moved off disk isn't greyed out; it's cleared automatically the next time you open it, with a brief notice, instead of opening a broken window.

Every word you type has to appear somewhere in a command's name or its search terms, but the order does not matter and the words do not have to sit next to each other: `branch switch` and `switch branch` both reach **Switch worktree**. Commands also carry the words people search by rather than only the words in their names, so `delete file` reaches **Move to Trash** and `open settings` reaches **Settings**. Because commands are listed above file results, a query that matches both will highlight the command — arrow down to reach the file, or keep typing to narrow.

A `tag:` prefix searches by tag: `tag:` alone lists every tag, `tag:fr` narrows the tag list, and `tag:frontend` lists the docs tagged `#frontend` (including its hierarchy children). When semantic search is enabled and the endpoint has either a stored key or a loopback address that needs none, a **By meaning** pill switches the palette to meaning-based search. Press Enter to run it; typing alone never fires a query.

## Sidebars and window width

The editor has two sidebars on opposite sides of the document: the file sidebar, on the left by default, and the document panel, on the right by default (Outline, Links, Graph, Timeline, Problems and Comments; single-file windows show Outline, Problems and Comments). To swap them, right-click an empty part of the editor's tab row and choose **Swap file sidebar and document panel**, or search the command palette for it. The choice is remembered, in the desktop app for every project, and each sidebar's show and hide button moves with it, to the side its sidebar opens from. Single-file windows have no file sidebar, so their document panel stays on its default side. Both sidebars adapt to the window:

- At comfortable widths (1280px and up) both sidebars open by default.
- Between 1024px and 1279px the document panel defaults to collapsed so the editor keeps its breathing room; the file sidebar stays open.
- Below 1024px both default to collapsed so the editor canvas isn't squeezed off-screen.
- When GitQuire is opened inside an AI editor's webview (Cursor, Codex, Claude Desktop), both sidebars start collapsed regardless of width; the embedded view is for reading the content you were sent, not for file management.

GitQuire remembers your explicit Show / Hide choice for each sidebar across reloads, at every window width. When there is not enough room to dock a sidebar beside a usable document, GitQuire temporarily hides it without changing that choice. Requesting the sidebar while it cannot dock opens it as a full-editor cover. **Back to editor** returns to the document without turning the sidebar off. **Hide panel** in the document panel cover's header, or **Hide Files** in the file sidebar's **Tree view options** menu, closes it explicitly, so widening does not reopen it. As space returns, a sidebar hidden only for fit can dock again.

### When the header runs out of room

At any window width, when the header has no room for all of its controls, the presence avatars for agents and collaborators, **Share**, sync, settings and resources move into a **More actions** menu. The menu sits on the right side of the header, just before the **Editor**, **Agents** and **Terminal** buttons, which always stay outside it. Pages that point to those controls on the right of the header mean this menu while it is showing.

## Application menus

The GitQuire desktop app keeps its menu bar in sync with the active editor target: File menu items enable / disable based on whether a doc, folder, or nothing is currently selected. On macOS this is the system menu bar; on Windows and Linux the same menus live in the app window's title bar, with `Ctrl` in place of `Cmd`.

On Windows and Linux, an open dialog such as Settings blocks the title-bar menus until you close it, the way a dialog blocks its window's menus in other Windows and Linux apps. Pressing `Ctrl+,` while Settings is open keeps it open on the page you were viewing; close it with the X button or `Esc`.

### File menu

Alongside the project items (Recent project, New project…, Switch Project… `Cmd+Shift+P`, Open Folder… `Cmd+O`), the worktree pair (New worktree…, Switch worktree…), **Set up GitQuire integrations…** (re-runs the first-launch integrations setup), and Close tab, the File menu surfaces the most-used sidebar affordances so they're reachable from the keyboard:

| Item | Accelerator | Behavior |
| --- | --- | --- |
| **New File** | `Cmd+N` | Creates a new file at the project root (or under the active folder if one is selected). |
| **New Folder** | `Cmd+Shift+N` | Creates a new folder. |
| **New from Template…** | (none) | Opens the template picker. |
| **Duplicate** | `Cmd+D` | Duplicates the active file or folder. Disabled when nothing is selected. |
| **Rename** | (none) | Inline-renames the active file or folder. Disabled when nothing is selected. |
| **Move to Trash** | `Cmd+Delete` | Sends the active file or folder to the OS trash (with the same confirm modal as the sidebar). On Windows the item reads **Move to Recycle Bin**. Disabled when nothing is selected. |
| **Reveal in Finder** | (none) | Reveals the active target in your file manager. The label adapts per platform — **Reveal in File Explorer** on Windows, **Open containing folder** on Linux. Empty selection reveals the project root. |
| **Copy Path ▸** | (none) | Full / Relative path of the active target. |

### Edit menu

Alongside the standard Undo / Redo / Cut / Copy / Paste / Select All items:

| Item | Accelerator | Behavior |
| --- | --- | --- |
| **Check Spelling While Typing** | (none) | Checkbox reflecting whether spell check is on. Toggling applies app-wide and persists across relaunches — it's the same switch the editor right-click menu's Disable / Enable Spell Check rows flip (see [Right-click menu and spell check](#right-click-menu-and-spell-check)). |

### View menu

Before the existing Zoom and Toggle Fullscreen items, the View menu gets:

| Item | Accelerator | Bound to |
| --- | --- | --- |
| **Show / Hide Sidebar** | `Cmd+Option+S` | Toggles the file sidebar. Label flips between Show and Hide based on current state, matching Finder. |
| **Show / Hide Document Panel** | `Cmd+Option+B` | Toggles the document panel. |
| **Show / Hide Editor** | (none) | Toggles the editor, in project windows only (see [Hide the editor](#hide-the-editor)). Label flips between Show and Hide like the other toggles. |
| **Show / Hide Terminal** | `Cmd+J` / `Ctrl+J` | Toggles the Terminal in its current placement. (`` Ctrl+` `` toggles it too, though that chord has no menu accelerator.) |

Toggling the menu checkboxes flips the underlying config field, which propagates back to the sidebar via the standard CRDT subscription; both surfaces stay synchronized.

## Real-time collaboration

Everything in the editor (body, frontmatter, sidebar toggles) is backed by a CRDT. You and multiple AI agents writing through MCP can edit the same doc concurrently. Per-user presence is shown on the right of the header at the top of the window; the **agent activity** view ([Agent activity](./agent-activity.mdx)) groups every burst of agent edits with per-burst diffs and selective undo.

For recovery + history, see [Timeline and recovery](./timeline-and-recovery.mdx).
